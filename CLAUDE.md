## Project Status

Django project scaffolded (project name: `entryrecorder`), with a `recorder` app owning the truck-entry model, views, and its own `urls.py`. `entryrecorder/urls.py` handles project-level concerns (`admin/`, `login/`, `logout/`) and delegates everything else to `recorder.urls` via `include('recorder.urls')`. A login page, a home page with a records table backed by real seeded data, and the static/template plumbing are in place.

Beyond the initial read-only table, the home page now supports row selection (checkboxes), inline edit, bulk delete, server-side pagination (30/page) with date/vehicle-number search, PDF export (with a dynamically-ranged "Save by Range" picker for large record counts), and grouping entries into named **Batches**; batches have their own list/detail/edit pages. See "Entries: Selection, Bulk Actions & Editing", "PDF Export", "Batches", and "Notifications (Toasts)" below for how these fit together. The header's "Account Setting" button also now works — see "Account Settings" below.

The codebase has since been through a full FIND+FIX pass from four specialized review agents — refactor (cross-file duplication/dead code), cleancode (per-site code-quality/reliability), security, and responsive/mobile — whose fixes are threaded into the relevant sections below rather than collected in one place (search this file for "audit" to find them all). Notable ones: `/login/` now has a lockout (see "Auth"), `check_username`/`forgot_password_request_otp` are rate-limited (see "Forgot Password"), `DEBUG` is env-controlled with production cookie/transport hardening staged behind it (see "Before Adding Code"), and several mobile touch-target/viewport/modal-scroll fixes landed across the home page, batch cards, and the login page (see "Frontend JS Structure" and the relevant page sections).

## Commands

- Activate venv: `source venv/Scripts/activate` (bash) or `.\venv\Scripts\Activate.ps1` (PowerShell)

- Run migrations: `python manage.py migrate`
- Run tests: `python manage.py test` (single test: `python manage.py test <app>.tests.<TestCase>.<test_method>`)

## What This Project Is

Entry Recorder is a web app (not a mobile app) for a **single user** to log **Truck Loading Records**. See `PROJECT.md` for the full definition, goals, and status checklist — read it before starting implementation work, since it holds context this file intentionally doesn't duplicate.

Key constraints to keep in mind when making architectural decisions:

- **Single user only** — no auth/multi-account/roles system should be introduced unless the client explicitly asks for it later.
- **Core entity is a truck loading entry** — `recorder.models.Entry`, backing the home page table columns: S.No, Date, Vehicle Number, then **a global Loading group (Loading/Roll, Net Kg (Loading/Roll), Workers) followed by three repeated Weight/Roll groups — Plant 5, Plant 6, Warp Plant** (each just Weight/Roll, Net Kg (Weight/Roll), Workers), then Remark. This is the client's (the app owner's father's) real-world workflow: rolls are packed/weighed separately at each of his three physical plants, then physically mix together and get loaded onto the truck as one combined operation by one shared group of loading workers — so Loading is genuinely global, not per-plant, while each plant only tracks its own packing/weighing stage. The model went through three reshapes from an original simpler layout (S.No, Date, Vehicle Number, Rolls, Workers, Net Kg, Remark): `recorder/migrations/0006_entry_new_table_format.py` split a single Rolls/Net Kg pair into Loading/Roll + Weight/Roll pairs (`rolls`→`loading_roll`, `net_kg`→`net_kg_loading_roll`, both `RenameField`; `weight_roll`/`net_kg_weight_roll` were new, backfilled to `0`); `recorder/migrations/0012_entry_multi_plant.py` then split that single 5-field group into 3 plant-prefixed groups (`loading_roll`→`plant5_loading_roll` etc., `RenameField`, so production data carried over as "Plant 5"; `plant6_*`/`warp_*` were new, nullable); `recorder/migrations/0013_entry_global_loading.py` then corrected the mistaken assumption that loading was per-plant too — `plant5_loading_roll`/`plant5_net_kg_loading_roll`/`plant5_workers` were **renamed back** to global, un-prefixed `loading_roll`/`net_kg_loading_roll`/`workers` (this also restores their true original pre-multi-plant meaning, since the app's real historical `workers` data was always a loading-worker count, never plant-specific), Plant 5 got a brand-new `plant5_workers` field for its own packing workers, and `plant6_loading_roll`/`plant6_net_kg_loading_roll`/`warp_loading_roll`/`warp_net_kg_loading_roll` (always null, never meaningful once loading became global) were dropped entirely (`RemoveField`). Each of the 4 groups' `verbose_name`s are deliberately **bare** (`'Loading/Roll'`/`'Net Kg (Loading/Roll)'`/`'Weight/Roll'`/`'Net Kg (Weight/Roll)'`/`'Workers'`) rather than group-prefixed — group identity comes from surrounding context (the New/Edit Entry form's `<fieldset><legend>` per group, the admin's `fieldsets`, and the table/PDF's group header row) everywhere these are rendered, not from the label text itself. S.No isn't a stored field — it's `forloop.counter` in the template (except on the home page, which annotates a stable `serial_number` via `Window(RowNumber())` ordered by `id` ascending, so row numbers don't reshuffle when sorted by date); the model's own auto PK (`id`) is what "auto include" refers to. This exact query (`Entry.objects.annotate(serial_number=Window(expression=RowNumber(), order_by=F('id').asc()))`) is a single module-level `entries_with_serial_number()` function in `recorder/models.py` (docstring explains the filter-then-window trap it exists to prevent, see "PDF Export" below), called from `home()`/`download_entries_pdf()` in `recorder/views.py` and from the test helpers in `recorder/tests.py` rather than each re-declaring the query. `date` is a plain `DateField(default=timezone.localdate)` — it defaults to today on a new entry but is user-editable in both New Entry and Edit Entry (rendered via `forms.DateInput(attrs={'type': 'date'})` in `EntryForm` for a native date picker); it was originally `auto_now_add=True`/non-editable, changed later so a backdated/forward-dated entry can be recorded deliberately. `vehicle_number` is a plain `CharField(max_length=150, null=True, blank=True)` — it originally had a Regex-validated Indian-plate format, widened progressively across `recorder/migrations/0008`–`0010` into unrestricted free text (a phrase, for trucks that don't report a number) as the field's max length grew; only `save()`'s uppercasing remains. All 12 numeric fields (`loading_roll`/`net_kg_loading_roll` global, plus `plant5_weight_roll`/`plant5_net_kg_weight_roll`/`plant6_weight_roll`/`plant6_net_kg_weight_roll`/`warp_weight_roll`/`warp_net_kg_weight_roll`) are `DecimalField(max_digits=10, decimal_places=2, null=True, blank=True, validators=[MinValueValidator(0)])` (upgraded from `PositiveIntegerField` by `recorder/migrations/0011_alter_entry_loading_roll_and_more.py` to allow decimals), and the 4 Workers fields (`workers` global, `plant5_workers`, `plant6_workers`, `warp_workers`) are `PositiveIntegerField(null=True, blank=True)`; every Net Kg field is rendered with a literal `" kg"` suffix in the templates/PDF (not stored in the DB). `remark` is optional free text and stays the last column. Keep the model easy to extend rather than hard-coded around exactly these columns.
- `recorder/management/commands/seed_entries.py` seeds **1000** randomly-generated entries by default (`python manage.py seed_entries`; pass `--count N` to seed a different amount, e.g. `--count 20`) spread randomly across the last 365 days. It's additive/rerunnable — no dedupe — so running it twice (or with `--count`) just adds more rows on top of whatever's already there. Rewritten from an original 10-hardcoded-row version once real load-testing of the PDF export / "Save by Range" picker (see "PDF Export" below) needed four-figure row counts to exercise properly. Uses `Entry.objects.bulk_create()` in batches of 500 rather than one `.create()` per row (performance, at 1000+ rows) — which means `Entry.save()`'s uppercasing of `vehicle_number` is **bypassed**, so the generator (`random_vehicle_number()`) builds numbers pre-uppercased itself rather than relying on `save()` to normalize them. `build_entry()` always populates the global Loading fields (`random_loading_values()` — every truck gets loaded, so this isn't conditional) and populates the 3 plants' Weight/Roll groups (`random_plant_values()`, one call per active plant) for **~70%** of generated rows; the remaining ~30% only populate 1-2 randomly-chosen plants (`random.sample`), leaving the untouched plant's whole 3-field group `None` — mirrors real usage (a plant can be idle for a given truck/day, or a load can be sourced from just 1-2 of the 3 plants) and exercises the "—" null-display path for a whole plant group in seeded/demo data, not just an individual field.
- **Batches group entries** — `recorder.models.Batch` (`name`, `slug`, `created_at`) and `Entry.batches` (`ManyToManyField(Batch, related_name='entries')`). **An entry can belong to multiple batches at once** — this was a deliberate correction mid-development: it was first built as a `ForeignKey` (one batch per entry), which was wrong; it's now M2M specifically so the same entry can be grouped into, say, both a "Morning Dispatch" batch and a "Customer X" batch simultaneously. See "Batches" below.
- Basic CRUD is now fully built: entries can be **created**, **edited**, and **deleted** (individually or in bulk) from the home page, and grouped into batches. List/filter/search over historical entries beyond batch grouping isn't built yet; avoid building analytics/reporting beyond that unless requested.

## Auth

- **Decision:** single Django superuser account is used for both the custom app login and the `/admin` panel — no separate credential store, since there is only one real user of this app.
- Wired via Django's built-in `django.contrib.auth.views.LoginView`/`LogoutView` at `/login/` and `/logout/` (`entryrecorder/urls.py`). `home` view (`recorder/views.py`, routed via `recorder/urls.py`) is `@login_required`. `LOGIN_URL`, `LOGIN_REDIRECT_URL`, `LOGOUT_REDIRECT_URL` are set in `settings.py`.
- **No superuser exists in the database yet.** Run `python manage.py createsuperuser` manually (interactively, so the password is actually yours) before login can work.
- **`/login/` is routed through `ThrottledLoginView`** (`recorder/views.py`, wired in place of the stock `LoginView` in `entryrecorder/urls.py`), not the bare Django `LoginView` — added after a security audit flagged that unlimited password guessing was possible against a known username. It's a minimal cache-backed lockout (`LOGIN_MAX_ATTEMPTS = 5` wrong attempts within `LOGIN_LOCKOUT_SECONDS = 15 * 60` locks out further attempts, including a subsequent *correct* password, since this project deliberately doesn't pull in `django-axes` or similar) keyed by the submitted username (lowercased, matching this app's `__iexact` convention elsewhere) rather than IP, so a shared IP/NAT doesn't lock out unrelated users — moot in practice since there's only ever one real account, but keeps the key meaningful. `form_invalid` increments the counter, `form_valid` clears it, and `post()` short-circuits with a locked-out form (no `authenticate()` call at all) once the cap is hit. `templates/registration/login.html`'s error block used to show the same generic "Your username and password didn't match" text for *any* form error regardless of content — it now special-cases the lockout's own message (checks for `'Too many failed login attempts'` in `form.non_field_errors.0`) so a locked-out user sees a distinct message instead of being told their password was simply wrong.

## Forgot Password

- `templates/registration/login.html` has a "Forgot Password?" button (`#forgot-password-btn`, styled with the same `button.btn-outline` pill class as Account Setting) directly under Log In. It's **disabled until the Username field's value matches the account's real username** — `static/js/src/login.js` debounces (~400ms) an `input` listener on `#id_username` that POSTs to `forgot-password/check-username/` and toggles `disabled` on the result. This runs before login, so there's no session yet — all four endpoints below are unauthenticated.
- **`check_username` is rate-limited per-IP** (`CHECK_USERNAME_MAX_ATTEMPTS = 20` within `CHECK_USERNAME_ATTEMPTS_TTL_SECONDS = 5 * 60`, cache counter keyed by `check_username_attempts:<REMOTE_ADDR>`) — added after a security audit flagged that this endpoint, with only a cosmetic ~400ms client-side debounce and no server-side throttle, was an unthrottled username-enumeration oracle. Once the cap is hit it returns `{'valid': False}` with HTTP 429, the same response shape as a genuine miss, so the throttle itself isn't distinguishable from a real lookup failure.
- Clicking it opens `#forgot-password-modal` (plain markup in `login.html`, not a separate partial since this page deliberately doesn't extend `base.html`), a 3-step flow (email → OTP → new password) reusing the same `.modal-overlay`/`.modal-card`/`.modal-actions`/`.modal-btn`/`.form-note` classes Account Settings already introduced — no new modal CSS needed.
- Backend (`recorder/views.py`, routed under `forgot-password/...` in `recorder/urls.py`): `check_username`, `forgot_password_request_otp`, `forgot_password_verify_otp`, `forgot_password_reset`. All username lookups use `username__iexact` — Django's own `ModelBackend` authenticates case-insensitively on username (`UserManager.get_by_natural_key`), so "correct username" has to mean the same thing here that it means at actual login.
- `forgot_password_request_otp` deliberately returns the **same** `"Enter Correct Email"` error whether the username doesn't exist or the email just doesn't match that user's stored `email` — this was an explicit requirement, and also means this step can't be used to enumerate valid usernames via trial-and-error emails. On a real match it emails a 6-digit OTP (same cache-based pattern as Account Settings' `change_email_request_otp`, 5 min TTL, 60s resend cooldown).
- **Wrong-email guesses against a known username are now rate-limited too** (`FORGOT_PASSWORD_EMAIL_MAX_ATTEMPTS = 5` within `FORGOT_PASSWORD_EMAIL_ATTEMPTS_TTL_SECONDS = 10 * 60`, cache counter keyed by `forgot_password_email_attempts:<user.pk>`, cleared on a successful match) — a security audit found the cooldown/attempt-cap machinery below only ever engaged *after* a correct email match, so a wrong-email guess previously returned the generic error with zero throttling, letting an attacker who already knows the username (e.g. via `check_username`) brute-force the registered email indefinitely. Once the cap is hit, **even a correct email is rejected with the identical generic `"Enter Correct Email"` message** — this is required to preserve the original enumeration-resistance property (the response must never reveal whether a mismatch or a throttle triggered).
- `forgot_password_verify_otp` mints a one-time **reset token** (`secrets.token_urlsafe(32)`, cached → user pk, 10 min TTL) on a correct OTP — this is what step 3 (`forgot_password_reset`) requires instead of re-sending the OTP, mirroring the reference implementation this was modeled on. The token is deleted the moment it's used (or the moment it expires from cache), so it can't be replayed.
- `forgot_password_reset` runs full `validate_password()` (same `AUTH_PASSWORD_VALIDATORS` as everywhere else) since this is a genuinely new password being chosen — unlike Account Settings' Cancel-revert path, there's no `revert=1`-style bypass here. On success, `login.js` does `window.location.href = '/login/'` (full reload, not a client-side reset) so the admin lands back on a clean login page.
- No IP-based lockout on the OTP-verification step itself (`_check_otp`'s existing 5-attempt cap covers guessing the OTP code once it's been sent) — a per-account cooldown + attempt cap is judged enough for a single local admin, not a publicly-reachable multi-tenant surface. This is a conscious tradeoff, not an oversight — see `/login/`'s own lockout above and `check_username`'s rate limit above for the two enumeration/brute-force gaps that *were* judged worth closing regardless of that tradeoff.

## Account Settings

- The header's "Account Setting" button (`base.html`, next to Logout on every authenticated page) opens `#account-settings-modal` (`templates/partials/account_settings_modal.html`, included from `base.html` and gated on `user.is_authenticated`, same convention as `confirm_modal.html`) — three independent sections (Username, Password, Email), each with its own Save/Send button that persists **immediately** to the server, not a single combined form submitted once.
- **Cancel** (button, Escape, or backdrop click — all funnel through the same handler) reverts everything changed during that modal session; **Done** just closes it and reloads the page only if the username changed (so the home page's `{{ user.get_username }}` greeting picks it up). This mirrors a UX correction made in the reference implementation this was modeled on: saving shouldn't itself close the modal or feel final until Done is clicked. All of this state lives in plain variables inside `static/js/src/account-settings.js` (`usernameChanged`, `originalPassword`/`currentPassword`, `emailChanged`) — there's no server-side "draft" concept.
- **`revertPendingChanges()` now actually checks whether its revert POSTs succeeded before letting Cancel close the modal.** A code-quality audit found it previously fired the username/password/email revert calls via `Promise.allSettled` but never inspected the results — so if any one revert failed (a 4xx from `postForm`, or an actual network-level rejection), `handleCancel()` still unconditionally reset the form state and closed the modal as if everything had reverted, silently leaving the account's *changed* value live while the UI implied Cancel had undone it. `revertPendingChanges()` now returns `true` only if every task both settled `fulfilled` and came back `ok`; `handleCancel()` checks that return value and shows an error toast instead of closing the modal on failure.
- Backend: five `@login_required @require_POST` views in `recorder/views.py` (`change_username`, `change_password`, `change_email_request_otp`, `change_email_verify`, `change_email_revert`), routed under `account/...` in `recorder/urls.py`, all returning `JsonResponse` (same style as `delete_entries`/`create_batch`) and called via `fetch` + `URLSearchParams` bodies from the JS above — not DRF, not JSON request bodies, to stay consistent with the rest of this app.
- **Username** revert just re-calls `change_username` with the original name (read once from `data-username` on the modal's root element). **Password** revert re-calls `change_password` with old/new swapped, but passes `revert=1` — **this flag is required**: `change_password` normally runs `validate_password()` (the same `AUTH_PASSWORD_VALIDATORS` from `settings.py`) against the new value, and it was discovered live that the account's *actual* password can itself fail `UserAttributeSimilarityValidator` against the account's own email, which would make Cancel permanently unable to restore it. `revert=1` skips that check; `check_password(old_password)` still has to match first, so this doesn't weaken normal password changes.
- **Email** uses a real OTP: `change_email_request_otp` emails a 6-digit code to the *new* address (not the current one) via `send_mail`, cached under `account_email_otp:<user id>` for 5 minutes with a 60s resend cooldown and a 5-attempt cap; `change_email_verify` checks it and, on match, stashes the outgoing address under `account_email_revert:<user id>` (30 min TTL) before overwriting `user.email` — that's what `change_email_revert` restores on Cancel. The reference implementation this was modeled on also had IP-based lockout/rate-limiting on top of this; that was deliberately left out here since this is a single local admin, not a publicly-reachable multi-admin app.
- OTP/cooldown/revert state lives in Django's default cache (no new model/migration) — fine for the single-process `runserver` this project runs under; would need a shared cache backend (e.g. Redis) if this ever ran under multiple worker processes.

## Entries: Selection, Bulk Actions & Editing

- **Creating** an entry: a "+ New Record" link/button (`.new-entry-bar`, right-aligned, same breakout width as `.page-header`/`.table-wrapper`) sits directly below the greeting on the home page, going to `entries/new/` (`create_entry` view, `templates/new_entry.html`) — **a plain page + form, not a modal**, deliberately matching `edit_entry.html`'s existing pattern exactly (same `EntryForm`, same `{% for field in form %}` rendering, same Save/Cancel — Cancel is just a link back to `home`, no JS, no revert logic). This was a deliberate simplification mid-request: it was first going to be a modal styled like Account Settings' (immediate-save sections + Cancel-reverts/Done-locks-in), but there's nothing to revert for a single brand-new record, so the user asked for the simpler existing edit-page pattern instead.
- **Pagination:** the home table shows `HOME_PAGE_SIZE` (30, `recorder/views.py` — was 25 initially, bumped once the client tried it live) rows per page via Django's `Paginator`, with a `.pagination` bar below the table (`templates/home.html`), hidden entirely when everything fits on one page (`{% if page_obj.paginator.num_pages > 1 %}`). Added once real usage grew the table past the point a single unpaginated page was reasonable — previously documented here as a known future gap.
  - **Four links, not two** — First/Prev/Next/Last, not just Prev/Next — the client wanted a direct jump to the first/last page in addition to one-page-at-a-time stepping. **This exact same 4-link pattern is used on both the home page and the Batch list page** (`templates/batch.html`) — the client explicitly asked for it everywhere pagination exists, not just home, after first seeing it only on home.
  - **Icon-only buttons grouped under one shared text label per side**, not 4 separately-labelled buttons (`« First`, `‹ Prev`, `Next ›`, `Last »` each with their own word) — an explicit design correction after the first pass shipped with per-button text labels and the client wanted it to instead read as a single "Prev" label governing both backward icons (`«` step, `««` jump-to-first) and a single "Next" label governing both forward icons (`»` step, `»»` jump-to-last), based on a reference sketch. Markup: `.pagination-group` (one on each side) wraps the label `<span class="pagination-group-label">` plus its two `.pagination-link.pagination-icon` buttons, with a tighter internal `gap` (`0.5rem`) than the outer `.pagination`'s `gap` (`1.5rem`) between the two groups and the status text — that gap difference is what visually reads as "these two icons belong to this label" rather than 4 evenly-spaced independent buttons.
  - Home's four links additionally share one `pagination_qs` string built once in the `home` view (`urlencode()` over whichever of `date`/`q`/`return_page` are active) rather than each link re-deriving its own `&date=...&q=...` suffix inline in the template — `?page=N{{ pagination_qs }}` per link. Batch has no filters, so its links are just plain `?page=N`. Note `pagination_qs` renders HTML-escaped (`&` → `&amp;`) same as any other template variable, unlike the old inline-literal-`&` version; that's the technically-correct form for an href attribute and both render identically in a browser, but it did need one existing test's assertion string updated to match.
  - **Extracted into `templates/partials/pagination.html`** once it became clear both pages needed the exact same First/Prev/Next/Last markup — same `{% include %}` convention as `entries_table.html`/`confirm_modal.html` (see "Templates" below): reads `page_obj` and `pagination_qs` straight off the parent template's context (no `only` on the `{% include %}`, so they're inherited rather than needing to be passed explicitly), and each page passes just the two words that differ — `{% include "partials/pagination.html" with pagination_noun_singular="entry" pagination_noun_plural="entries" %}` on home, `"batch"`/`"batches"` on batch.html — used instead of Django's `pluralize` filter since `entry → entries` isn't a simple suffix (`y → ies`) the way `batch → batches` is (`+es`), so the partial just picks between two fully-spelled-out words based on `page_obj.paginator.count == 1`. If a third paginated page/list is ever added, it should reach for this same partial rather than re-copying the markup a third time.
  - **Date/vehicle-number filtering moved server-side in the same change**, and this is the part worth understanding if touching either: the date/search inputs (`#date-filter-input`/`#entry-search-input`, see markup below) used to filter by hiding/showing whatever `<tr>`s were already in the DOM entirely client-side — that stopped being viable once only ~30 rows are ever in the DOM at once (filtering would've only ever searched the current page). They now navigate to `?date=YYYY-MM-DD`/`?q=<text>` (`applyFilters()`, see below) instead of touching the DOM, and `home` filters the queryset server-side (`date` exact match, `vehicle_number__icontains` for `q`) *before* paginating, so search/filter correctly narrows the whole dataset, not just one page. A malformed/tampered `date` param is silently ignored (caught via `date.fromisoformat`) rather than 500ing. Applying/changing either filter always resets to filtered-page 1. The empty-state message switches between "No entries yet." (nothing in the table at all) and "No matching entries." (a filter matched nothing) based on whether a filter is active — previously a separate client-side-only "No matching entries." row; now just `empty_message` in the `home` view's context, consumed by `entries_table.html`'s existing `{% empty %}` block. **`templates/partials/entries_table.html`'s `<tr>` no longer carries `data-date`/`data-vehicle` attributes** — a refactor pass found these were leftover from the pre-server-side client-side-filtering era above and confirmed (via a full grep across JS/CSS/templates) that nothing reads them anymore; they were removed as dead markup.
  - **`.date-filter` now wraps (`flex-wrap: wrap`) instead of forcing a single row**, and `.entry-search-input`'s width narrows to `200px` with `margin-left: 0` inside the existing 768px breakpoint — a responsive audit found the combined date input + calendar button + conditional "All" clear button + the included search bar (fixed 240px + 1.5rem left margin) summed to more width than a common ~375–414px phone viewport has, forcing horizontal scroll or visual clipping. The batch list's own search-only bar (`.batch-search-bar .entry-search-input { margin-left: 0; }`) was already fine on its own since it has no date input alongside it.

Caught by manually tracing the JS logic in Node before shipping (this app has no JS test runner) — if touching this again, retrace all three cases (page 1 start, page N start, immediate clear with no pagination) rather than trusting it by inspection.

## PDF Export

- **Save** button (`#save-pdf-btn`, home page's `.new-entry-actions`) opens `#save-modal` (`templates/home.html`), a menu of `.save-option-btn` buttons: `All Records`, `Last 10`, `Last 50`, `Last 100`, `Save by Range` (see below), `Choose`. Each (except `Save by Range`, which opens a sub-modal instead — see below) carries a `data-scope` read by `static/js/src/home.js` and POSTed straight to `download_entries_pdf` (`recorder/views.py`, `entries/download-pdf/`), which streams back a `reportlab`-built landscape-A4 PDF via `downloadPdf()` (`static/js/src/lib/download-pdf.js`, fetch-as-blob rather than a direct navigation, so the filename from `Content-Disposition` survives). `PDF_SCOPE_LIMITS` maps `all`/`last_10`/`last_50`/`last_100` to a slice size off `Entry.objects.order_by('-id')` (`None` = unlimited). `choose` instead reads a repeated `ids` POST param (the currently-checked rows) and preserves `-id` display order regardless of click order. A `batch` scope also exists, used only by `batch.js`'s per-batch download, not this modal.
- **"Save by Range"** (`#by-range-btn` — named "After 100" during development, renamed once the client saw it in context and wanted something more descriptive) is a **second, stacked modal** (`#range-modal`) that opens **on top of** `#save-modal` without closing it — the first place in this codebase two `.modal-overlay`s are ever simultaneously `.visible` (every other modal here is mutually exclusive). It lists dynamically-generated 100-record range buttons (`101-200`, `201-300`, …) built client-side by `buildRanges(entryCount)` in `home.js`: starting at `boundary = 100`, keep adding `[boundary+1, boundary+100]` and advancing `boundary += 100` **while** `entryCount - boundary > 20` — i.e. the next range only appears once more than 20 records exist past the last shown boundary, so a count like 1000 stops at `901-1000` (`1000-1000` isn't `>20`) while 1021 extends one more step to `1001-1100`. `entryCount` comes from `Entry.objects.count()`, computed fresh in the `home` view and exposed via `data-entry-count` on `#selection-bar` (same convention as its other `data-*-url` attributes) rather than a separate fetch. If `buildRanges` returns empty (≤120 records), clicking it just closes `#save-modal` and shows a toast ("No more records beyond the first 100.") instead of opening an empty modal.
  - A `1-100` button sits last in the range grid (after the dynamic `101-200`, `201-300`, … buttons, so the grid reads as one continuous countdown toward the start of the ledger) — the mirror image of "Last 100", added once the client noticed the range picker had no way to reach the *oldest* records. Wired to its own `first_100` scope rather than the generic `range` one: `range`'s `start`/`end` are positions counted from the *newest* end (`Entry.objects.order_by('-id')[start-1:end]`), so `start=1` there would just re-fetch the newest 100, not the oldest — `first_100` instead does `Entry.objects.order_by('id')[:100]` (ascending, oldest-first), and needs no S.No special-casing since these specific rows' real app serial_number already *is* `1..100`.
  - Backend: a `range` scope on `download_entries_pdf` takes `start`/`end` POST params (1-based, inclusive), validated as positive digits with `end >= start`, sliced off the same `-id` ordering as the `last_N` scopes (`Entry.objects.order_by('-id')[start-1:end]`) — a range is a continuation of "Last 100", not a different ordering. Filename becomes `truck-entries-range-{start}-{end}-<date>.pdf`.
  - **S.No is deliberately scope-dependent** — this was iterated on live with the client and is easy to get backwards, so it's spelled out explicitly: `all`/`last_10`/`last_50`/`last_100`/`choose`/`batch` all show each entry's **real app serial_number** (the same value the home page's own S.No column shows for that row — confirmed correct against `Last 10`, which the client explicitly signed off on). `range` is the **one deliberate exception**: its S.No instead continues the range button's own label (`101-200` download → S.No `101, 102, ... 200`, capped short on a partial final range rather than overshooting to a phantom `200`) — a range download reads like "page 2 of the ledger", not a slice tagged with each row's real global number. An `all`-scope variant using this same ascending-from-1 style was tried and explicitly reverted by the client — don't reintroduce it without asking again.
  - **Real-serial-number bug (found and fixed via the test suite below):** `choose` and `batch` initially showed *locally* renumbered S.No (`1, 2, 3...`) instead of the real app serial_number, because `Window(RowNumber())` annotated on the same queryset a `.filter()` also runs on ranks only *within* the filtered subset — SQL evaluates `WHERE` before window functions execute, so e.g. `Entry.objects.annotate(serial_number=Window(...)).filter(pk__in=ids)` ranks only the 2-3 chosen rows, not the whole table. Fixed by ranking the *entire, unfiltered* table once into an `id -> serial_number` dict and looking values up by id afterward, sidestepping the filter-then-window trap entirely — see the `else` branch building `serial_by_id` in `download_entries_pdf`, which now calls the shared `entries_with_serial_number()` helper (see the model section above) instead of re-declaring the window-function query inline.
  - **`choose`'s "at least one entry" check now validates the resolved DB rows, not the raw id count.** A security audit found `len(ids) >= 1` could pass on an all-stale id list (rows deleted between page-load and click) while `Entry.objects.filter(pk__in=ids)` resolved to zero rows, silently producing a header-only PDF instead of the "Select at least one entry" error a genuinely empty selection gets. Now checks the materialized `entries` queryset's count instead. (The same fix — validating resolved rows instead of raw `len(ids)` — was applied to `create_batch`'s "at least two entries" check; see "Batches" below.)
  - **`entry.remark` is now escaped before being wrapped in ReportLab's `Paragraph()`** (`xml.sax.saxutils.escape(entry.remark) if entry.remark else '—'`, `recorder/views.py`) — a security audit found the raw field was previously passed straight into `Paragraph`, which interprets a small XML-like markup language (`<b>`, `<font color="...">`, `<a href="...">`, etc.) rather than treating the string as plain text. Unescaped, a remark containing a literal `&`/`<` broke PDF generation outright, and a remark crafted with valid ReportLab markup could render as a real clickable hyperlink in the exported PDF. Low real-world exploitability today (only the single logged-in admin can write a `remark`), but the fix is cheap and closes both the crash and the markup-injection angle for good — apply the same escaping to any other free-text field ever added to this PDF table.
  - **The header tuple and `colWidths` list in `download_entries_pdf` are declared ~40 lines apart** but must stay the same length and in the same column order — a code-quality audit flagged this as a fragile pairing (ReportLab fails loudly on a length mismatch, but a same-length reorder of one list without the other silently misaligns columns with no error). A comment now links the two so a future edit to either prompts checking the other. The PDF header is **16 columns across 2 physical rows** (S.No, Date, Vehicle Number, LR/Net Kg (L/R)/Wrk, then 3 sub-columns each for Plant 5/Plant 6/Warp Plant, then Remark) built with ReportLab `SPAN`s. Loading/Roll, Net Kg (L/R), and Workers (L/R) are **plain standalone columns, not a spanning sub-group** — they vertically span both header rows exactly like S.No/Date/Vehicle Number/Remark, deliberately *not* grouped under a "Loading" box the way the plants are, since loading is global (belongs at the same visual level as Date/Vehicle Number) while only the 3 real physical plants get the special grouped treatment (their names horizontally span their own 3 columns in row 0; row 1 carries the abbreviated sub-headers — `LR`/`WR`/`Wrk`/`Net Kg (L/R)`/`Net Kg (W/R)` rather than the fuller form field labels, to fit; a single unbroken word like "Workers" has no space for ReportLab's `Paragraph` to wrap at, so a column this narrow was breaking it one letter per line before the abbreviation). `templates/partials/entries_table.html`'s `<thead>` mirrors this exactly — `Loading/Roll`/`Net Kg (L/R)`/`Workers (L/R)` are plain `rowspan="2"` `<th>`s next to Vehicle Number, only Plant 5/6/Warp Plant get a `colspan="3"` group header. Every data/S.No/Date cell is also wrapped in a `Paragraph` (a dedicated `numeric_style`), not passed as a plain string — plain strings never wrap in a ReportLab Table cell, they just overflow straight into the next column with no visible gap, which is what caused a real overlapping-text bug reported against an early version of this multi-column layout. `colWidths` sums to 734pt, under the ~774pt usable landscape-A4 width at this doc's 12mm margins (`S.No`/`Date`/`Vehicle Number` are also sized generously enough to keep a 4-digit serial, a full `dd-mm-yyyy` date, and a ~10-char plate-style vehicle number each on one line — `extract_pdf_serial_numbers()`/`extract_pdf_vehicle_numbers()` in `recorder/tests.py` identify rows by matching a *whole* value on one text line, so a value split across two lines silently breaks those heuristics). `Table(..., repeatRows=2, ...)` so both header rows repeat on every page. The Total row sums **8 accumulators** (`loading_roll`/`net_kg_loading_roll` globally, plus `weight_roll`/`net_kg_weight_roll` per plant × 3) — Workers stays excluded from every total, consistent with the original single-group behavior — and still spans only S.No/Date/Vehicle Number via `SPAN`.
  - Stacking mechanics: `#range-modal` uses `z-index: 301` (an id selector, so it out-specifies `.modal-overlay`'s base `z-index: 300` without `!important`) and reuses the existing `#add-records-modal`/`#forgot-password-modal` convention of `max-height: 90vh; overflow-y: auto` on `.modal-card` for short viewports — `#save-modal` was missing from that same convention until a responsive audit caught it (short/landscape mobile viewports could make its Cancel button or last save-option unreachable); it's now in the same selector group as the other three. Body-scroll locking (`lockBodyScroll`/`unlockBodyScroll` in `static/js/src/lib/modal-dismiss.js`) is already reference-counted, so nesting two locks/unlocks needed no changes there — see "Frontend JS Structure" below for how that locking itself was hardened for iOS Safari. **Escape-key handling did need a fix**: `bindModalDismiss` attaches one document-level `keydown` listener per modal, so with both open, a single Escape press would fire both independently and close both at once. `closeSaveModal()` in `home.js` now checks `rangeModal.classList.contains("visible")` first and redirects to closing only the range modal if so — so Escape closes the topmost modal only, matching normal nested-modal UX (a second Escape then closes the parent). No amount of additional CSS closed the gap, so it was switched to a real `<button type="button">` to guarantee pixel-identical styling with its siblings.
- **Tests:** `recorder/tests.py` covers both S.No schemes above — `After100RangeExportTests` (125-row seed) and `After100RangeExportAtProductionScaleTests` (1121-row seed, matching the exact size manually tested when the real-serial-number bug was found) download every range button's PDF and assert the parsed S.No column equals `expected_range_sno()` (the range-label scheme); `LastNAndChooseExportMatchAppSerialNumberTests` asserts `last_10`/`choose` instead match `real_serial_numbers()` (the real-app-serial_number scheme) — this second class is what actually caught the `choose` filter-then-window bug above, not just a passing rubber-stamp. Both classes also cover `first_100` (S.No `1..100`, or `1..N` capped when the table has fewer than 100 rows). If a S.No mismatch is ever reported again, run `python manage.py test recorder` first to check whether it's a real backend regression before assuming it is one.
- **Careful with raw DB access while debugging this:** while chasing the `choose` bug above, an unguarded `manage.py shell -c "Entry.objects.all().delete()"` one-liner was run directly against the live `db.sqlite3` (meant to be a quick debug setup) instead of going through the test framework's isolated DB — it wiped the real seeded dataset. Recovered by reseeding (nothing manual was lost that time, only disposable `seed_entries` output, but it easily could have been real data). **Always reach for `recorder/tests.py`'s `TestCase` (isolated per-test DB) for anything resembling `Entry.objects.all().delete()` — never a raw shell one-liner against the live database.**
- **Bulk-selection field-count gotcha:** selecting **all** rows via `#select-all-rows` and then downloading (or bulk-deleting) used to silently fail once the table had over ~1000 entries — each selected id is posted as its own repeated form field (`ids=1&ids=2&...`), and Django's default `DATA_UPLOAD_MAX_NUMBER_FIELDS` (1000) rejects the request with `TooManyFieldsSent` **before the view even runs**, so the browser only ever saw the generic `downloadPdf()` fallback error ("Could not generate the PDF. Please try again.") with no real diagnostic. Fixed by setting `DATA_UPLOAD_MAX_NUMBER_FIELDS = 20000` in `settings.py` (safe to raise generously — single local admin, no untrusted form submitters). This same limit would have hit `delete_entries`'s bulk delete identically at the same row count; the fix covers both.

## Batches

- `recorder.models.Batch`: `name`, `slug` (`SlugField`, unique, auto-generated from `name` via `slugify()` in `save()` with a `-2`/`-3`/… suffix loop on collision), `created_at`. **The slug is generated once and never regenerated on rename** — renaming a batch keeps its existing slug/URL stable rather than breaking bookmarks/links.
- `Entry.batches` is `ManyToManyField(Batch, related_name='entries')` — so `batch_obj.entries` gives its entries and `entry_obj.batches` gives its batches. Deleting a `Batch` just clears the join-table rows (M2M has no `on_delete` config to get wrong); the entries themselves are never touched by a batch delete.
- **`create_batch`'s "at least two entries" check validates the resolved DB rows, not the raw `ids` count.** A security audit found `len(ids) >= 2` could pass on a partly- or fully-stale id list (rows deleted between page-load and the Group click) while `Entry.objects.filter(pk__in=ids)` resolved to fewer than 2 (even zero) real rows, letting a batch get created that violates its own "at least two" invariant. Now checks `len(entries)` after materializing the queryset instead — same fix applied to `download_entries_pdf`'s `choose` scope, see "PDF Export" above.
- **Batch list page** (`/batch/`, `batch.html`) renders batches as cards (`.batch-grid`/`.batch-card`, not a table), 4 per row via `grid-template-columns: repeat(4, 1fr)` (2 under 768px, 1 under 480px), breaking out to the same wide `-200px`-margin width as the home page's `.table-wrapper`/`.page-header` rather than staying boxed into the narrow `.container` — dark border + drop shadow by default, background turns gray on hover. Paginated to `BATCH_PAGE_SIZE` (40 — the client specifically wants **10 rows** of cards, not 10 cards, so this is 10 rows x the grid's 4-per-row column count; `recorder/views.py`) via the same `Paginator` + `.pagination` bar pattern as the home page (see "Pagination" above), with search-by-name (see below) narrowing the queryset before pagination the same way home's date/vehicle-number filter does. The card grid's `{% for batch in batches %}` loop variable is spelled out in full (`batch`, not the single-letter `b` an earlier pass used) — a code-quality audit flagged `b` as the one outlier against every other template in this project naming its loop variable after the real-world entity. Each card has a three-dot menu button (top-right, `.batch-card-menu-btn`, sized to a proper 44px/`2.75rem` touch target — bumped up from 40px after a responsive audit, with `.batch-card-menu`'s `top` offset nudged to match) toggling a small dropdown (`.batch-card-menu`) with **Edit** (plain link to the edit page) and **Delete** (confirm-modal + POST to `batch/<slug>/delete/`) — handled by `static/js/src/batch.js`. `.batch-card-menu-item`'s padding was also increased toward a 44px effective height and `.batch-card-menu-delete` gained a `border-top` separator from the item above it, both from the same responsive audit, to reduce mis-tap risk against the destructive Delete option. **Delete no longer just does `card.remove()`** — that shipped fine pre-pagination, but once pagination arrived it left a visible gap (39 cards instead of 40) since removing one DOM node has no way to know page 2's first card should slide up into the vacated slot. - **Batch detail page** (`/batch/<slug>/`, `batch_detail.html`) is read-only: batch name as the heading, a plain table of its entries (same columns as home, no checkboxes), a "Back to Batches" link.
- **Batch edit page** (`/batch/<slug>/edit/`, `batch_edit.html`) is a single Django view (`batch_edit`) branching on a hidden `action` field (`rename` / `remove` / `add`) from **plain HTML forms** — deliberately *not* AJAX/fetch, so it reuses Django's messages framework (and therefore the toast system) for free instead of needing a parallel JS notification path:
  - The batch name is rendered as an editable text input styled to look like a heading (`.batch-name-input`, transparent background, bottom border only) with its own "Save Name" button — renaming does not change the slug (see above).
  - **Exactly one table** is shown: "Grouped Records", with a checkbox per row and a "Remove Selected from Batch" button below it (`action=remove`) — this only removes the selected entries from *this* batch (`batch_obj.entries.remove(...)`), it does not delete the entries or touch their membership in any other batch. Both the `remove` and `add` branches now call `messages.error(...)` when submitted with nothing selected (previously only the sibling `rename` branch did this — a code-quality audit found `remove`/`add` silently reloaded the page with zero feedback on an empty submission, indistinguishable from a slow page load, since these are plain HTML forms with no client-side disable-on-empty-selection logic).
  - A **"+ Add" button** sits to the right of the "Grouped Records" heading (`.section-header`, flex `space-between`). Clicking it opens a modal (`#add-records-modal`, wider variant via `.modal-card-wide`, scrollable table via `.modal-table-wrapper` with a sticky header) listing every entry **not already in this specific batch** — critically, `available_entries = Entry.objects.exclude(batches=batch_obj)`, **not** `.filter(batches__isnull=True)`. The latter would incorrectly hide entries that are already grouped into some *other* batch, which contradicts the "an entry can be in multiple batches" decision above. The modal is itself a real `<form action=add>`; "Done" is its submit button (no fetch needed), "Cancel" just closes the modal (`static/js/src/batch-edit.js` — the only JS on this page, purely open/close/Escape/backdrop-click, no data logic).
- Migration note: `Entry.batch` (FK) → `Entry.batches` (M2M) was a hand-written migration (`recorder/migrations/0004_entry_batches_m2m.py`) rather than `makemigrations`-generated, because converting FK→M2M isn't a single automatic operation — it adds the M2M field under a temporary name/related_name (to avoid a `related_name='entries'` clash with the old FK while both exist mid-migration), copies every existing `batch_id` into it via `RunPython`, drops the old FK column, then renames the field to `batches`. If touching batch membership at the model level again, expect a similarly multi-step hand-written migration, and back up `db.sqlite3` first if real batch data exists.

- **Netlify was the first deployment target requested and was ruled out** — it's a static-site/serverless-function host with no persistent process, no writable/persistent filesystem, and no support for Django's session/cache backend or a real database. This app is fully stateful (server-rendered templates, login sessions, SQLite/Postgres, SMTP OTP emails, PDF generation), so Netlify was never viable for it; don't reintroduce Netlify config. **Render** was picked instead — free tier, no credit card, deploys straight from the GitHub repo (`origin` → `github.com/shahbazkhan74659-crypto/RecordEntryApp`), supports a real persistent Postgres alongside the web service.

Order matters: `collectstatic` must run before the app serves any request (WhiteNoise's manifest storage — see below — 404s on unbuilt/uncollected assets), and `migrate` running in the build step (not a separate release phase) means a bad migration fails the build itself rather than shipping a broken app.
- **`gunicorn`** is the production WSGI server (`Procfile`: `web: gunicorn entryrecorder.wsgi:application`, and `render.yaml`'s own `startCommand` duplicates this for Render specifically since Render doesn't read `Procfile` by default). `gunicorn` does not run on Windows (relies on `fork`) — this was verified by running the actual production path (`DEBUG=False`, `gunicorn`, real Postgres) inside a throwaway Docker Postgres container from a Linux-compatible check instead; `runserver` under `DEBUG=False` was used as a Windows-compatible proxy to verify WhiteNoise/static behavior specifically, since `runserver` skips its own dev-mode static serving once `DEBUG=False`, matching how WhiteNoise serves it in real production.
- **WhiteNoise** (`whitenoise.middleware.WhiteNoiseMiddleware`, added to `MIDDLEWARE` right after `SecurityMiddleware`) serves static files directly from the app process — no separate static file host/CDN needed for a single-user app this size. `STORAGES['staticfiles']` is **conditionally** `whitenoise.storage.CompressedManifestStaticFilesStorage` only when `DEBUG=False`; it falls back to Django's plain `StaticFilesStorage` when `DEBUG=True`. This distinction matters and broke once during setup: manifest storage requires `collectstatic` to have already run (it resolves `{% static %}` tags against a generated hash-manifest file), which local dev/`manage.py test` never do — leaving it unconditionally on the manifest backend made every `{% static %}` tag raise `ValueError: Missing staticfiles manifest entry` under the test runner (caught by running the full test suite against Postgres before trusting the config, not by inspection).
- **`recorder/migrations/0003_batch_slug.py` had a real Postgres-only bug**, found by actually running `migrate` against a fresh Postgres database (SQLite masked it completely) — the migration's `AddField` step for `Batch.slug` didn't set `db_index=False` explicitly, so `SlugField`'s own default (`db_index=True`) let it silently create both a plain index and a Postgres-specific `_like` opclass index; the very next operation in the same migration (`AlterField` adding `unique=True`) then tried to create an index with the same deterministic name and failed with `relation "recorder_batch_slug_..._like" already exists`. Fixed by adding `db_index=False` to that `AddField`'s field definition — the final schema (a unique index) is unchanged, only the redundant intermediate index creation is removed. **This migration has already been applied on any existing SQLite database**, including the real seeded one — Django only checks migration *names* against `django_migrations`, not content, so this edit is a no-op there and only matters for a fresh database (Postgres on Render, or any new local DB).
- **Verification before trusting any of this**: a throwaway Postgres container (`docker run postgres:16-alpine`) was used to run `migrate`, `makemigrations --check --dry-run` (confirmed zero model/migration drift), the full `manage.py test recorder` suite (all 40 tests), and an actual login + home-page request cycle end-to-end — not just a settings.py read-through. The full `build.sh` pipeline (npm build → `collectstatic` → `migrate`) was also run against a fresh Postgres container to mirror Render's real build step exactly, followed by a `DEBUG=False` + `X-Forwarded-Proto: https` request cycle to confirm WhiteNoise serves the correct manifest-hashed filename in production mode. All containers were removed after verification; nothing from this process was left running or persisted.
- **What was manual** (done once, not automatable from this repo): creating the Render account and the Blueprint instance itself (named `LoadGate_Entries` in the dashboard — cosmetic label only, doesn't affect the `entryrecorder`/`entryrecorder-db` resource names, which come from `render.yaml`), and filling in `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD` plus `DJANGO_SUPERUSER_USERNAME`/`DJANGO_SUPERUSER_EMAIL`/`DJANGO_SUPERUSER_PASSWORD` in the Render dashboard (all `sync: false` in `render.yaml`, never committed) — this project intentionally has no seeded/default superuser (see "Auth" above), and that constraint carries over to production. All five are now set; if the production superuser's credentials are ever forgotten, they can't be read back out (Django only stores the hash) — reset by changing `DJANGO_SUPERUSER_PASSWORD` won't help either, since the bootstrap below only *creates*, it never updates an existing user; use Account Settings' own password-change flow (logged in as that user) or the Forgot Password flow instead.
- **Gotcha found live: adding new `sync: false` keys to `render.yaml` for an *already-existing* service does not auto-populate blank fields on the next sync**, only on the *original* Blueprint Apply. When `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD` were added at initial creation, Render's Apply-review screen prompted for their values inline. Later, when the three `DJANGO_SUPERUSER_*` keys were added to `render.yaml` after the service already existed, neither the automatic post-push deploy nor a manual **Manual Sync** on the Blueprint added them to the service's Environment tab (`Manual Sync` reported "Resources already up to date" — it only diffs service/database *structure*, not blank `sync: false` keys on an existing service). Fix was to add the three keys **by hand** directly on the web service's Environment tab (Add Environment Variable), which then correctly stuck (protected from being overwritten by future syncs, exactly what `sync: false` is for) and triggered the redeploy that ran the bootstrap. **If more `sync: false` env vars are ever added to an existing service in `render.yaml`, expect to add them manually in the dashboard too — don't assume a sync will surface them.**
- **`createsuperuser` can't be run interactively in production the way the docs originally assumed** — Render's Shell tab (and One-Off Jobs) require a paid instance type; the free web-service plan has no Shell access at all. `build.sh` instead bootstraps the superuser itself on every deploy, from the three `DJANGO_SUPERUSER_*` env vars above, via a `User.objects.filter(username__iexact=...).exists()` check (same case-insensitive convention as the rest of Auth) so it only ever creates the account once — safe to leave the block running on every subsequent build/redeploy. If those three env vars are ever unset, the block just no-ops (guarded by `[ -n "$DJANGO_SUPERUSER_USERNAME" ]`), so it's harmless on a fresh Blueprint sync before they're filled in.

## Before Adding Code

- **`DEBUG` is now env-controlled, not hardcoded** — `entryrecorder/settings.py` reads `DEBUG = os.environ.get('DEBUG', 'False') == 'True'` (defaults `False`), and the gitignored `.env` sets `DEBUG=True` for local dev (documented in `.env.example` too). A security audit found `DEBUG` had been hardcoded `True` since the project's first commit with no way to flip it for a real deployment short of a manual source edit — the single biggest concrete production-readiness gap found, since a stray unhandled exception on a publicly-reachable instance would render Django's full debug traceback (stack, local variables, request data, file paths) to anyone who triggers it. `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` are now env-controlled too (comma-separated, see `.env.example`) and both auto-append Render's own `RENDER_EXTERNAL_HOSTNAME` env var when present, so a plain Render Blueprint deploy needs zero manual hostname configuration — see "Deployment (Render)" below.
- **Production cookie/transport hardening settings exist but are inert during local dev** — `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_SSL_REDIRECT`, `SECURE_HSTS_SECONDS` (+ `INCLUDE_SUBDOMAINS`/`PRELOAD`), and `SECURE_PROXY_SSL_HEADER` were added to `entryrecorder/settings.py`, all gated on `not DEBUG` so they resolve to their dev-safe/inert values whenever `.env`'s `DEBUG=True` and only activate once a real deployment sets `DEBUG=False`. The deployment topology is now known (Render): its edge proxy terminates real TLS and sets `X-Forwarded-Proto` on every request, so trusting `SECURE_PROXY_SSL_HEADER` is safe there specifically — this would NOT be safe on a host where an untrusted party could set that header directly.
