## Project Status

Django project scaffolded (project name: `entryrecorder`), with a `recorder` app owning the truck-entry model, views, and its own `urls.py`. `entryrecorder/urls.py` handles project-level concerns (`admin/`, `login/`, `logout/`) and delegates everything else to `recorder.urls` via `include('recorder.urls')`. A login page, a home page with a records table backed by real seeded data, and the static/template plumbing are in place.

Beyond the initial read-only table, the home page now supports row selection (checkboxes), inline edit, bulk delete, and grouping entries into named **Batches**; batches have their own list/detail/edit pages. See "Entries: Selection, Bulk Actions & Editing", "Batches", and "Notifications (Toasts)" below for how these fit together. The header's "Account Setting" button also now works — see "Account Settings" below.

## Commands

- Activate venv: `source venv/Scripts/activate` (bash) or `.\venv\Scripts\Activate.ps1` (PowerShell)
- Run dev server: `python manage.py runserver`
- Run migrations: `python manage.py migrate`
- Run tests: `python manage.py test` (single test: `python manage.py test <app>.tests.<TestCase>.<test_method>`)
- Install deps: `pip install -r requirements.txt`; after adding a package, refresh with `pip freeze > requirements.txt`
- Frontend JS build (from repo root, needs Node.js): `npm install`, then `npm run build` (one-off bundle) or `npm run watch` (rebuild on save) — run this alongside `runserver` in a separate terminal while editing anything under `static/js/src/`. `npm run lint` runs ESLint.

- **Backend:** Python, Django

- **Frontend:** Django templates (server-rendered) for markup; a small Node/esbuild pipeline (`package.json`, `eslint.config.js`) bundles client-side JS from `static/js/src/*.js` to `static/js/dist/*.js` (gitignored build output — must run `npm run build` after cloning or pulling JS changes). ## What This Project Is

Entry Recorder is a web app (not a mobile app) for a **single user** to log **Truck Loading Records**. See `PROJECT.md` for the full definition, goals, and status checklist — read it before starting implementation work, since it holds context this file intentionally doesn't duplicate.

Key constraints to keep in mind when making architectural decisions:

- **Single user only** — no auth/multi-account/roles system should be introduced unless the client explicitly asks for it later.
- **Core entity is a truck loading entry** — `recorder.models.Entry`, backing the home page table columns: S.No, Date, Vehicle Number, Rolls, Workers, Net Kg, Remark (superseding the original 5-field placeholder list in `PROJECT.md`; "Packing" was dropped and "Trucks Loaded" was replaced by per-row Vehicle Number/S.No/Date). S.No isn't a stored field — it's `forloop.counter` in the template (except on the home page, which annotates a stable `serial_number` via `Window(RowNumber())` ordered by `id` ascending, so row numbers don't reshuffle when sorted by date); the model's own auto PK (`id`) is what "auto include" refers to. `date` is a plain `DateField(default=timezone.localdate)` — it defaults to today on a new entry but is user-editable in both New Entry and Edit Entry (rendered via `forms.DateInput(attrs={'type': 'date'})` in `EntryForm` for a native date picker); it was originally `auto_now_add=True`/non-editable, changed later so a backdated/forward-dated entry can be recorded deliberately. `vehicle_number` is validated against an Indian plate format (`^[A-Z]{2}[0-9]{1,2}[A-Z]{1,3}[0-9]{4}$`, case-insensitive on input) and normalized to uppercase in `save()` — the validator's regex must stay case-insensitive since normalization happens *after* validation runs. `rolls`/`workers`/`net_kg` are `PositiveIntegerField`; `net_kg` is rendered with a literal `" kg"` suffix in `home.html` (not stored in the DB). `remark` is optional free text. Keep the model easy to extend rather than hard-coded around exactly these columns.
- `recorder/management/commands/seed_entries.py` seeds 10 sample entries spread across the last 10 days (`python manage.py seed_entries`). It's additive/rerunnable — no dedupe — so running it twice doubles the rows. Dates are backdated by passing `date=` straight to `Entry.objects.create()` — now that `date` isn't `auto_now_add` anymore, this no longer needs the old two-step `create()` + `.update()` bypass.
- **Batches group entries** — `recorder.models.Batch` (`name`, `slug`, `created_at`) and `Entry.batches` (`ManyToManyField(Batch, related_name='entries')`). **An entry can belong to multiple batches at once** — this was a deliberate correction mid-development: it was first built as a `ForeignKey` (one batch per entry), which was wrong; it's now M2M specifically so the same entry can be grouped into, say, both a "Morning Dispatch" batch and a "Customer X" batch simultaneously. See "Batches" below.
- Basic CRUD is now fully built: entries can be **created**, **edited**, and **deleted** (individually or in bulk) from the home page, and grouped into batches. List/filter/search over historical entries beyond batch grouping isn't built yet; avoid building analytics/reporting beyond that unless requested.

## Auth

- **Decision:** single Django superuser account is used for both the custom app login and the `/admin` panel — no separate credential store, since there is only one real user of this app.
- Wired via Django's built-in `django.contrib.auth.views.LoginView`/`LogoutView` at `/login/` and `/logout/` (`entryrecorder/urls.py`). `home` view (`recorder/views.py`, routed via `recorder/urls.py`) is `@login_required`. `LOGIN_URL`, `LOGIN_REDIRECT_URL`, `LOGOUT_REDIRECT_URL` are set in `settings.py`.
- **No superuser exists in the database yet.** Run `python manage.py createsuperuser` manually (interactively, so the password is actually yours) before login can work.

## Forgot Password

- `templates/registration/login.html` has a "Forgot Password?" button (`#forgot-password-btn`, styled with the same `button.btn-outline` pill class as Account Setting) directly under Log In. It's **disabled until the Username field's value matches the account's real username** — `static/js/src/login.js` debounces (~400ms) an `input` listener on `#id_username` that POSTs to `forgot-password/check-username/` and toggles `disabled` on the result. This runs before login, so there's no session yet — all four endpoints below are unauthenticated.
- Clicking it opens `#forgot-password-modal` (plain markup in `login.html`, not a separate partial since this page deliberately doesn't extend `base.html`), a 3-step flow (email → OTP → new password) reusing the same `.modal-overlay`/`.modal-card`/`.modal-actions`/`.modal-btn`/`.form-note` classes Account Settings already introduced — no new modal CSS needed.
- Backend (`recorder/views.py`, routed under `forgot-password/...` in `recorder/urls.py`): `check_username`, `forgot_password_request_otp`, `forgot_password_verify_otp`, `forgot_password_reset`. All username lookups use `username__iexact` — Django's own `ModelBackend` authenticates case-insensitively on username (`UserManager.get_by_natural_key`), so "correct username" has to mean the same thing here that it means at actual login.
- `forgot_password_request_otp` deliberately returns the **same** `"Enter Correct Email"` error whether the username doesn't exist or the email just doesn't match that user's stored `email` — this was an explicit requirement, and also means this step can't be used to enumerate valid usernames via trial-and-error emails. On a real match it emails a 6-digit OTP (same cache-based pattern as Account Settings' `change_email_request_otp`, 5 min TTL, 60s resend cooldown).
- `forgot_password_verify_otp` mints a one-time **reset token** (`secrets.token_urlsafe(32)`, cached → user pk, 10 min TTL) on a correct OTP — this is what step 3 (`forgot_password_reset`) requires instead of re-sending the OTP, mirroring the reference implementation this was modeled on. The token is deleted the moment it's used (or the moment it expires from cache), so it can't be replayed.
- `forgot_password_reset` runs full `validate_password()` (same `AUTH_PASSWORD_VALIDATORS` as everywhere else) since this is a genuinely new password being chosen — unlike Account Settings' Cancel-revert path, there's no `revert=1`-style bypass here. On success, `login.js` does `window.location.href = '/login/'` (full reload, not a client-side reset) so the admin lands back on a clean login page.
- No IP-based lockout — same simplification already made for Account Settings' email OTP (see below): a per-account cooldown + 5-attempt cap is enough for a single local admin, not a publicly-reachable multi-tenant surface.

## Account Settings

- The header's "Account Setting" button (`base.html`, next to Logout on every authenticated page) opens `#account-settings-modal` (`templates/partials/account_settings_modal.html`, included from `base.html` and gated on `user.is_authenticated`, same convention as `confirm_modal.html`) — three independent sections (Username, Password, Email), each with its own Save/Send button that persists **immediately** to the server, not a single combined form submitted once.
- **Cancel** (button, Escape, or backdrop click — all funnel through the same handler) reverts everything changed during that modal session; **Done** just closes it and reloads the page only if the username changed (so the home page's `{{ user.get_username }}` greeting picks it up). This mirrors a UX correction made in the reference implementation this was modeled on: saving shouldn't itself close the modal or feel final until Done is clicked. All of this state lives in plain variables inside `static/js/src/account-settings.js` (`usernameChanged`, `originalPassword`/`currentPassword`, `emailChanged`) — there's no server-side "draft" concept.
- Backend: five `@login_required @require_POST` views in `recorder/views.py` (`change_username`, `change_password`, `change_email_request_otp`, `change_email_verify`, `change_email_revert`), routed under `account/...` in `recorder/urls.py`, all returning `JsonResponse` (same style as `delete_entries`/`create_batch`) and called via `fetch` + `URLSearchParams` bodies from the JS above — not DRF, not JSON request bodies, to stay consistent with the rest of this app.
- **Username** revert just re-calls `change_username` with the original name (read once from `data-username` on the modal's root element). **Password** revert re-calls `change_password` with old/new swapped, but passes `revert=1` — **this flag is required**: `change_password` normally runs `validate_password()` (the same `AUTH_PASSWORD_VALIDATORS` from `settings.py`) against the new value, and it was discovered live that the account's *actual* password can itself fail `UserAttributeSimilarityValidator` against the account's own email, which would make Cancel permanently unable to restore it. `revert=1` skips that check; `check_password(old_password)` still has to match first, so this doesn't weaken normal password changes.
- **Email** uses a real OTP: `change_email_request_otp` emails a 6-digit code to the *new* address (not the current one) via `send_mail`, cached under `account_email_otp:<user id>` for 5 minutes with a 60s resend cooldown and a 5-attempt cap; `change_email_verify` checks it and, on match, stashes the outgoing address under `account_email_revert:<user id>` (30 min TTL) before overwriting `user.email` — that's what `change_email_revert` restores on Cancel. The reference implementation this was modeled on also had IP-based lockout/rate-limiting on top of this; that was deliberately left out here since this is a single local admin, not a publicly-reachable multi-admin app.
- OTP/cooldown/revert state lives in Django's default cache (no new model/migration) — fine for the single-process `runserver` this project runs under; would need a shared cache backend (e.g. Redis) if this ever ran under multiple worker processes.

## Entries: Selection, Bulk Actions & Editing

- **Creating** an entry: a "+ New Record" link/button (`.new-entry-bar`, right-aligned, same breakout width as `.page-header`/`.table-wrapper`) sits directly below the greeting on the home page, going to `entries/new/` (`create_entry` view, `templates/new_entry.html`) — **a plain page + form, not a modal**, deliberately matching `edit_entry.html`'s existing pattern exactly (same `EntryForm`, same `{% for field in form %}` rendering, same Save/Cancel — Cancel is just a link back to `home`, no JS, no revert logic). This was a deliberate simplification mid-request: it was first going to be a modal styled like Account Settings' (immediate-save sections + Cancel-reverts/Done-locks-in), but there's nothing to revert for a single brand-new record, so the user asked for the simpler existing edit-page pattern instead.
- The home table's first column (`.col-select`) has a checkbox per row (`.row-select`, `value` = entry id), **plus a "select all" checkbox in the header cell itself** (`#select-all-rows`) that checks/unchecks every row at once. It also reflects row state the other way: `updateSelectAllState()` in `static/js/src/home.js` (called from the same `updateBar()` every other selection change already runs through) sets it fully checked only when every row is checked, and `.indeterminate` when some-but-not-all are — so it stays in sync whether rows are toggled individually, via delete/group clearing them, or via the header checkbox itself. Checking any row (or the header checkbox) toggles `.selected` on the relevant `<tr>`(s) and shows a floating **selection bar** (`#selection-bar`, fixed bottom-center, `backdrop-filter: blur`, slides up via `.visible`) with three icon-only square buttons in a fixed order: **Edit** (blue), **Group** (violet), **Delete** (red) — all share the same `.btn-edit`/`.btn-group`/`.btn-delete` base rule (same 40×40px rounded-square shape, only color differs).
- Enable/disable rules (`updateBar()` in `static/js/src/home.js`), each button independently reflecting what bulk action is actually valid for the current selection count:
  - **Edit** — enabled only when exactly 1 row is selected (`edit_entry` takes a single pk); disabled (dimmed, `cursor: not-allowed`) otherwise.
  - **Group** — enabled only when 2+ rows are selected (grouping 0 or 1 entries is meaningless); blocked at exactly 1.
  - **Delete** — enabled whenever 1+ rows are selected (works for both single and bulk delete).
- **Edit** (`recorder/views.py:edit_entry`, `entries/<pk>/edit/`) is a normal Django `ModelForm` (`recorder/forms.py:EntryForm`, fields: `date`, `vehicle_number`, `rolls`, `workers`, `net_kg`, `remark` — `date` renders as an HTML5 date picker and is user-editable) rendered at `templates/edit_entry.html`; POST validates, saves, and redirects to `home` with a success message. JS navigates there via a `data-edit-url-template` URL (`{% url 'edit_entry' pk=0 %}`) with the literal `/0/` segment swapped for the real id client-side, since the target id isn't known until a row is checked.
- **Delete** (`recorder/views.py:delete_entries`, POST-only `entries/delete/`) takes `ids[]`, does a single `Entry.objects.filter(pk__in=ids).delete()`, returns JSON. Before the request fires, a **custom confirm modal is used instead of the browser's native `window.confirm()`** — an explicit requirement, since the native dialog can't be styled. The shared modal markup lives in `templates/partials/confirm_modal.html` (included by both `home.html` and `batch.html`) and its open/resolve/cancel logic lives in `static/js/src/lib/confirm-dialog.js` (`confirmDialog(message)`, returns a `Promise<boolean>`, resolves `false` on Cancel/Escape/backdrop-click). On success, rows are removed from the DOM and a toast fires with the `"error"` tag (see Notifications below) — a deliberate reuse of the red/error toast styling for a *successful* destructive action, not a literal error.
- **Group** opens a second, distinct modal (`#group-modal`, home.html-only, not shared) prompting for a batch name via `promptDialog()` (same Promise pattern as `confirmDialog`, but resolves the typed name or `null`). POSTs to `entries/group/` (`create_batch`) which requires 2+ ids and a non-empty name; see "Batches" below for what happens next.
- `getCookie()` (CSRF token read from the `csrftoken` cookie) and `confirmDialog()` are shared via `static/js/src/lib/` and imported into both `home.js` and `batch.js` — see "Frontend JS Structure" below for why this split exists.

## Batches

- `recorder.models.Batch`: `name`, `slug` (`SlugField`, unique, auto-generated from `name` via `slugify()` in `save()` with a `-2`/`-3`/… suffix loop on collision), `created_at`. **The slug is generated once and never regenerated on rename** — renaming a batch keeps its existing slug/URL stable rather than breaking bookmarks/links.
- `Entry.batches` is `ManyToManyField(Batch, related_name='entries')` — so `batch_obj.entries` gives its entries and `entry_obj.batches` gives its batches. Deleting a `Batch` just clears the join-table rows (M2M has no `on_delete` config to get wrong); the entries themselves are never touched by a batch delete.
- **Batch list page** (`/batch/`, `batch.html`) renders batches as cards (`.batch-grid`/`.batch-card`, not a table) — dark border + drop shadow by default, background turns gray on hover. Each card has a three-dot menu button (top-right, `.batch-card-menu-btn`) toggling a small dropdown (`.batch-card-menu`) with **Edit** (plain link to the edit page) and **Delete** (confirm-modal + POST to `batch/<slug>/delete/`, then the card is removed from the DOM and a red toast fires) — handled by `static/js/src/batch.js`. The card's own body is a separate inner `<a>` (`.batch-card-link`) to the detail page, kept as a sibling of the menu button rather than nesting the button inside the `<a>`, since nesting interactive elements inside an `<a>` is invalid HTML and would make the menu button also trigger navigation.
- **Batch detail page** (`/batch/<slug>/`, `batch_detail.html`) is read-only: batch name as the heading, a plain table of its entries (same columns as home, no checkboxes), a "Back to Batches" link.
- **Batch edit page** (`/batch/<slug>/edit/`, `batch_edit.html`) is a single Django view (`batch_edit`) branching on a hidden `action` field (`rename` / `remove` / `add`) from **plain HTML forms** — deliberately *not* AJAX/fetch, so it reuses Django's messages framework (and therefore the toast system) for free instead of needing a parallel JS notification path:
  - The batch name is rendered as an editable text input styled to look like a heading (`.batch-name-input`, transparent background, bottom border only) with its own "Save Name" button — renaming does not change the slug (see above).
  - **Exactly one table** is shown: "Grouped Records", with a checkbox per row and a "Remove Selected from Batch" button below it (`action=remove`) — this only removes the selected entries from *this* batch (`batch_obj.entries.remove(...)`), it does not delete the entries or touch their membership in any other batch.
  - A **"+ Add" button** sits to the right of the "Grouped Records" heading (`.section-header`, flex `space-between`). Clicking it opens a modal (`#add-records-modal`, wider variant via `.modal-card-wide`, scrollable table via `.modal-table-wrapper` with a sticky header) listing every entry **not already in this specific batch** — critically, `available_entries = Entry.objects.exclude(batches=batch_obj)`, **not** `.filter(batches__isnull=True)`. The latter would incorrectly hide entries that are already grouped into some *other* batch, which contradicts the "an entry can be in multiple batches" decision above. The modal is itself a real `<form action=add>`; "Done" is its submit button (no fetch needed), "Cancel" just closes the modal (`static/js/src/batch-edit.js` — the only JS on this page, purely open/close/Escape/backdrop-click, no data logic).
- Migration note: `Entry.batch` (FK) → `Entry.batches` (M2M) was a hand-written migration (`recorder/migrations/0004_entry_batches_m2m.py`) rather than `makemigrations`-generated, because converting FK→M2M isn't a single automatic operation — it adds the M2M field under a temporary name/related_name (to avoid a `related_name='entries'` clash with the old FK while both exist mid-migration), copies every existing `batch_id` into it via `RunPython`, drops the old FK column, then renames the field to `batches`. If touching batch membership at the model level again, expect a similarly multi-step hand-written migration, and back up `db.sqlite3` first if real batch data exists.

## Notifications (Toasts)

- Django's `{% if messages %}` block in `base.html` no longer renders an inline banner — messages now render as **bottom-right popup toasts** (`.messages`, `position: fixed; right: 24px; bottom: 24px`), each auto-dismissing after exactly **5 seconds** via a slide/fade transition (`static/js/src/messages.js`).
- `messages.js` exposes `window.showToast(text, tag)` globally (not just for server-rendered Django messages) — it creates the `.messages` container on demand if one doesn't already exist on the page. This lets purely client-side flows (e.g. the AJAX bulk-delete on the home page, batch deletion from the card menu) show the exact same toast without a page reload/redirect.
- `tag` maps to CSS classes `.message.success` (green) / `.message.error` (red) — **`"error"` is deliberately reused for the delete-confirmation toasts** ("Deleted N entries.", "Deleted batch "X".") even though nothing actually errored; this was an explicit styling request ("just in red") rather than a semantic use of Django's error level. Don't read `tag="error"` in this codebase as "something failed."

## Templates

- `templates/base.html` — shared layout (header with brand + nav, messages block, footer, a `scripts` block) used by `home.html` and any future authenticated pages. The brand block (`.brand-group`: `LOGO2.png` + "Entry Recorder" text) is **plain text/image, not a link** — it was a link (`<a href="/">`) originally, then deliberately un-linked. Instead, explicit **"Home" and "Batch" nav links** (`.nav-link`, shared class so both get identical styling) sit immediately right of the brand, nudged left as a group via `margin-left: -0.75rem` on `.brand-group`. Whichever page you're on gets a `active` class (via `{% if request.resolver_match.url_name == 'home' %}` / `== 'batch'` — `django.template.context_processors.request` must stay enabled in `settings.py` for this to work) which triggers a one-time CSS `@keyframes` animation growing a glowing red underline in from the left (`transform: scaleX(0) → scaleX(1)`, persists via `animation-fill-mode: forwards` for as long as the `active` class is present, i.e. for as long as you're on that page). It also unconditionally includes `partials/account_settings_modal.html` (gated on `user.is_authenticated`) and loads `account-settings.js` for authenticated pages — see "Account Settings" above.
- `templates/partials/admin_greeting.html`, `templates/partials/confirm_modal.html`, and `templates/partials/account_settings_modal.html` — small shared includes (`{% include %}`) factored out to avoid duplicating markup. Any new authenticated page showing the admin greeting or needing the delete-confirm modal should `{% include %}` those rather than re-inlining them; the Account Settings modal itself only needs including once, in `base.html`, since it's reachable from every authenticated page's header.
- `templates/edit_entry.html`, `templates/batch.html`, `templates/batch_detail.html`, `templates/batch_edit.html` — see "Entries: Selection, Bulk Actions & Editing" and "Batches" above for what each does.
- `templates/registration/login.html` — **deliberately does not extend `base.html`** (an explicit decision to fully decouple the login page from the shared layout). It's a standalone HTML document with its own `<head>`/`<body>`, pulling in only `style.css`, `login.js`, and the logo. `body.login-page` is locked to `height: 100vh; overflow: hidden` with flexbox centering, so the login page never scrolls and the logo+card stay vertically/horizontally centered regardless of viewport height.
- `templates/home.html` — the records table page. The header nav (in `base.html`, shared across authenticated pages) shows "Account Setting" (now a working button opening the modal above — no longer the `href="#"` placeholder) and Logout (no "Entries" link, removed intentionally). The table is wrapped in `.table-wrapper`, which deliberately breaks out ~60px past the normal container width on each side (not full viewport — that was tried and explicitly dialed back) for a wider look, collapsing to normal width under 768px. The header row itself (`.header-inner`) and a `.page-header` wrapper (containing the `<h1 class="page-title">` and the admin greeting) use the same breakout so header, heading, and table all share matching left/right edges.
- `.page-header` is a flex row (`justify-content: space-between`) holding `<h1 class="page-title">Truck Loading Entries</h1>` and `<p class="admin-greeting">Administrator Dashboard | Welcome, {{ user.get_username }}</p>` — the greeting is dynamic (pulls the logged-in superuser's username), not hardcoded text.
- **`.header-inner` centering gotcha:** it carries both `.container` (`margin: 0 auto`) and its own rules. Giving it a fixed `margin-left`/`margin-right` to break out (like `.table-wrapper` does) conflicts with the inherited `margin: 0 auto` — the explicit longhand wins and the box loses centering instead of widening symmetrically (this shipped broken once: logo clipped off-screen left, Logout centered mid-page). The working fix is overriding `max-width` (currently `1040px`) instead, which coexists with the inherited auto-centering. If any element needs a breakout margin *and* already relies on `.container`'s auto-centering, use the `max-width` approach, not `margin-left`/`margin-right`.
- **`.site-nav a` specificity gotcha:** `.site-nav a` / `.site-nav a:hover` (class+type selector) are more specific than a lone `.btn-outline` class and will silently override its color/hover styles for any `<a>` placed inside `.site-nav` (this happened to the "Account Setting" button — text rendered muted-gray instead of black, blue on hover instead of white). Any future nav link/button that needs its own colors must use a type+class selector (`a.btn-outline`/`button.btn-outline`) to win the specificity tie via source order, or otherwise out-specificity `.site-nav a`. Account Setting itself is now a `<button>` (it opens a modal, not a navigation target), so `.btn-outline`'s CSS rule covers both `a.btn-outline` and `button.btn-outline`.
- Header buttons: `.btn-outline` (Account Setting) is a white/dark-bordered pill that inverts to solid black/white text on hover; `.link-button` (Logout) is a light-red pill with bold black text. Both share the same padding and a 2px border (transparent on `.link-button`) so their rendered heights match exactly — dropping the border from one without compensating breaks height parity.

## Frontend JS Structure

- `static/js/src/*.js` are separate esbuild entry points (one dist bundle each) matching the page that uses them: `home.js` (home page selection bar/modals), `batch.js` (batch list card menus), `batch-edit.js` (add-records modal open/close only — the batch-edit page's actual data actions are plain form POSTs, not JS), `messages.js` (toasts, loaded unconditionally in `base.html` so it's available on every page), `login.js` (unchanged, Zod validation), `account-settings.js` (the header's Account Settings modal — loaded in `base.html` for authenticated pages only, since the modal itself is gated the same way).
- `static/js/src/lib/` holds shared modules (`cookies.js`: `getCookie()`; `confirm-dialog.js`: `confirmDialog()`) imported via ES `import` into the page-specific entry files above. esbuild's glob (`static/js/src/*.js`) only picks up top-level files as entry points, but `--bundle` still traces and inlines anything they `import` from `lib/` — so `lib/*.js` files intentionally produce **no dist output of their own**; don't add them to the entry glob.
